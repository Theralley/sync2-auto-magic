# Development update: decoder, CarPlay priority and CPU clocks

We are working toward a custom decoder that is verified in the car, more responsive CarPlay,
and a controlled CPU overclock experiment on Ford SYNC 2. This is experimental development;
no faster decoder or higher CPU frequency has yet demonstrated a measured improvement in the car.

## What the car has shown

CarPlay, Maps and Spotify work on the test car. The current comparison uses **640×384,
10 fps, software decoding**. This smaller picture leaves black borders. Earlier measurements
showed lower load than 800×480, but the latest decoder-install attempt produced **no noticeable
improvement** in the same Maps/Spotify test. That observation does not identify which decoder
was running.

The first independent native inspection completed and recovered the active, backup and staged
decoder files. All three active files were still the originals; the staged files matched our
candidate. The subsequent revised installation returned without its verification report again.
Its package was consumed, but installation remains unverified until the new file capture returns.

We found a concrete reporting defect: calling MortScript's `DelTree` on a missing child can
remove its empty parent report directory. The behavior is present in both the
[interpreter implementation](https://github.com/hjgode/jscripts/blob/master/MortScript/CommandsFileReg.cpp#L170)
and the exact interpreter shipped with the test. The cleanup now checks that each child exists
and recreates the report directory. This explains how the report can disappear; it does not
prove what the second installation left on the car.

**The next USB package is an independent read-only inspection**, targeting that latest attempt.
It collects the three active DLLs, their backups and staged replacements for byte comparison.
It installs no decoder, changes no priority and raises no clock. The separate decoder undo
stick remains available. See the [inspection procedure](DECODER-INSPECTION.md).

## Goal 1: a custom decoder verified in the car

Our non-NEON FFmpeg build uses about **20% fewer emulated instructions** on the existing test
material, with matching decoded pictures. That is an emulator result, not a 20% CarPlay speed
gain. We still need to establish loading, picture and audio correctness, stability and useful
performance on the actual unit.

The sequence is to identify the installed files, resolve installation/reporting, then compare
original and candidate under the same resolution, priority, warm-up and Maps/Spotify workload.
Keep an independent set of original DLLs for restoration. Compare actual responsiveness and
CPU measurements before changing resolution or adding another optimization.

NEON remains a separate candidate. Static analysis found relevant register-context handling
in a firmware candidate, but a small instruction/context-switch test in the car must precede
a NEON decoder trial. See [performance work](PERFORMANCE.md) and the
[firmware analysis](CLOCK-FIRMWARE-ANALYSIS-2026-11-16.md#neon-follow-up-evidence).

## Goal 2: give foreground CarPlay more processor time

The existing 640×384 trace shows the busiest AutoKit thread at priority 252 using about 36%
of the CPU, while the main SYNC screen thread used about 17% at priority 250, sometimes 248.
The AutoKit thread is the likely decode bottleneck; CPU share alone is not a function trace.

The next scheduling comparison will try **250**, only while AutoKit is alone in the foreground,
and verify restoration to 252 when it loses that position. The existing guard supports this;
its job can now request a load recording. Raising priority reallocates CPU time. It neither
raises the clock nor reduces the amount of decoding work, and any benefit needs measurement.
SYNC's audio, USB, input and other required services remain running.

Use matched baseline and boosted runs. Inspect both the priority-change log and actual sampler
timestamps: the sampler itself has lower priority and may be delayed under load, so ten seconds
is an intended interval rather than a guaranteed cadence. CPU samples do not measure frame
rate or tap latency. Record repeated visible interactions as well.

## Goal 3: a controlled overclock experiment

We have recovered and analyzed clock/power modules from a firmware candidate whose metadata
matches the test car. No usable higher CPU operating point or frequency-setting driver has
been established. Candidate-image matching is not proof that all its bytes match the car.

The first standalone clock-read probe failed at memory mapping with error 87; it returned no
clock-register snapshot. Candidate CE6 code indicates that the physical-mapping path expects
a registered user-mode driver host. A separate temporary stream-driver prototype has now been
implemented and cross-compiled on the build server, with 18 focused tests and five existing
parser tests passing. It still needs independent review, integration and its first car run.
The prototype remains in a separate development worktree and is not included in this published
source snapshot.

That prototype only reads a fixed set of PLL1/CCM registers, validates its driver identity and
records cleanup. It contains no frequency or voltage change. A successful read would establish
live clock configuration, not an overclocking method by itself.

A later frequency trial needs a verified CPU transition and restoration path, understood clock
dependencies, and voltage/thermal evidence. A small increase around **620–630 MHz** remains a
research target, not a supported setting or a ready USB package. We have not measured CPU
temperature or established active voltage/headroom. Details: [clock method](CLOCK-METHOD.md),
[outcome plan](CLOCK-OUTCOMES.md) and [firmware analysis](CLOCK-FIRMWARE-ANALYSIS-2026-11-16.md).

## How results become progress

We publish successful and unsuccessful tests with their limits. Installation success screens,
emulator results, host tests and car measurements answer different questions. The next useful
result is the latest decoder's file identity; after that, decoder and priority comparisons can
be interpreted. Clock access and a frequency-changing experiment remain separate milestones.

This update publishes development source and documentation, not a release or prebuilt vehicle
package. Vehicle identifiers, captured firmware, proprietary application files and test-car
decoder binaries are not included.

Publication checks: 201 focused decoder, guard and theme tests pass without skips. Independent
security, performance and test reviews found an outdated decoder simulation, which was corrected
and re-reviewed. Documentation links, Python syntax and whitespace checks pass. Full CI was not
run for this experimental development update; these checks do not replace the pending car tests.
